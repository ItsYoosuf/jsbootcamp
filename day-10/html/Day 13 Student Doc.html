Topic 1 What is an Execution Context? Global · Function
Type Created when How many Holds
Global EC Script first loads Exactly 1 per program Top-level vars + functions, global this
Function EC Each function call One per call (fresh) Local vars, arguments, own this
Each EC is a "container" with: a Variable Environment (its locals), a reference to the outer scope, and a value of this. 
// One Global Execution Context for the whole file
const city = "Jaipur";          // lives in Global EC

function greet(name) {
  // A new Function EC is created on EACH call to greet()
  const message = `Hi ${name} from ${city}`;   // 'message' lives in this Function EC
  return message;
}

greet("Priya");                  // creates Function EC #1, then destroys it
greet("Aarav");                  // creates Function EC #2 (fresh — independent of #1)
Topic 2 The Two Phases Creation · Execution
Phase What happens Code runs?
1. Creation Engine scans, allocates memory for declarations No
2. Execution Engine runs code top-to-bottom, line by line Yes
Creation phase rules:
• var x → memory + value undefined
• let x / const x → memory, marked uninitialised (TDZ)
• function foo() {} → memory + entire body 
// What you wrote:
console.log(name);     // line 1
var name = "Priya";    // line 2
console.log(name);     // line 3

// What the engine effectively does:

// CREATION PHASE (before any line runs):
//   name → undefined        ← var allocated, default value

// EXECUTION PHASE (line by line):
//   line 1: console.log(name)   → undefined  (memory exists, value not yet set)
//   line 2: name = "Priya"      → assignment runs, name now holds "Priya"
//   line 3: console.log(name)   → "Priya"

Topic 3 The Call Stack LIFO — last in, first out
Event Stack action
Script starts Push Global EC
Function called Push Function EC on top
Function returns Pop top EC
Script ends Pop Global EC — stack empty 
function multiply(a, b) {
  return a * b;
}

function square(n) {
  return multiply(n, n);
}

function printSquare(n) {
  console.log(square(n));   // logs 25
}

printSquare(5);
The call stack at the EXACT moment multiply(5, 5) is executing:
┌────────────────────────────┐ │ multiply(5, 5) │ ← top of stack — currently running ├────────────────────────────┤ │ square(5) │ ├────────────────────────────┤ │ printSquare(5) │ ├────────────────────────────┤ │ Global Execution Context │ ← bottom — never goes until script ends └────────────────────────────┘
Topic 4 Hoisting — What It Actually Is Not "code moves up"
"Declarations move to the top" is a metaphor — useful, technically wrong. The engine simply sees declarations during the Creation phase and reserves their memory before line 1 runs. Source file is unchanged. 
// Each behaves differently:

console.log(a);        // undefined          ← var hoisted with undefined
var a = 1;

console.log(b);        // ReferenceError     ← let hoisted, but in TDZ
let b = 2;

console.log(c);        // ReferenceError     ← const hoisted, but in TDZ
const c = 3;

greet();               // "Hi"               ← function declaration: full body hoisted
function greet() { console.log("Hi"); }

Topic 5 var vs let / const + TDZ Temporal Dead Zone
Keyword Creation phase Before declaration line After declaration line
var allocated → undefined returns undefined returns assigned value
let allocated, uninitialised ReferenceError (TDZ) returns assigned value
const allocated, uninitialised ReferenceError (TDZ) returns assigned value
TDZ = Temporal Dead Zone. The window between the start of the block and the line where a let/const is declared. The variable EXISTS but is marked uninitialised. Accessing it throws. 
// var — silent undefined (the old, problematic behaviour)
console.log(score);    // undefined            ← no error, but probably not what you wanted
var score = 90;

// let — TDZ catches the bug for you
console.log(level);    // ReferenceError       ← TDZ — Cannot access 'level' before initialization
let level = 5;

// The TDZ "ends" exactly when the let/const line runs:
{
  // <-- start of block. 'mark' is in TDZ here
  // console.log(mark);  // would throw
  let mark = 87;
  console.log(mark);    // 87  ← TDZ has ended, mark is initialised
}
⚠️ var has another quirk — function-scoping. var is scoped to the nearest function, not the nearest block. So a var inside if / for leaks out of the block. let/const are block-scoped — what you'd intuitively expect. We'll see this again in Day 2 (Scope & Closures).

Topic 6 Function Declaration vs Expression The most common hoisting bug
Form Hoisted as Callable before its line?
function foo() {} Full function (memory + body) ✅ Yes
var foo = function () {} Variable as undefined ❌ TypeError
let foo = function () {} Variable in TDZ ❌ ReferenceError
const foo = () => {} Variable in TDZ ❌ ReferenceError 
// Function declaration — works BEFORE its definition
sayHi();           // "Hi"      ← full body hoisted
function sayHi() {
  console.log("Hi");
}

// Function expression with var — TypeError
greet();           // TypeError: greet is not a function
                   //   ↑ greet was hoisted with value 'undefined'.
                   //     Calling undefined() throws TypeError.
var greet = function () {
  console.log("Hello");
};

// Function expression with const — ReferenceError (TDZ)
welcome();         // ReferenceError: Cannot access 'welcome' before initialization
const welcome = function () {
  console.log("Welcome");
};

// Arrow function — same as const above (always TDZ if let/const)
shout();           // ReferenceError
const shout = () => console.log("HEY");

Topic 7 Why This Matters in Practice Real-world payoff
Where you'll meet hoisting What it explains
Reading legacy var-heavy code Why old jQuery / pre-2015 React class components behave oddly
TypeError: foo is not a function at top of file Function expression called before its assignment
Stack traces in error logs Each line is one EC frame, top is most recent
Linter warnings (no-var, no-use-before-define) The linter is preventing exactly these bugs
Rule of thumb: read var; write let/const. Don't rely on hoisting. Use it to explain bugs.

Task 1 Predict the var hoist
  • Type this exact snippet in a fresh JS file: console.log(name); var name = "Priya"; console.log(name);
  • BEFORE running it, predict what each console.log will print.
  • Now run it. Match your prediction against actual output.

Task 2 Trigger the TDZ
  • Type this snippet in a fresh JS file: console.log(city); let city = "Jaipur";

  • Note the EXACT error name and message.
  • Move the let city = "Jaipur" line ABOVE the console.log. Verify the file now runs.

Task 3 Function declaration vs expression
  • Create a JS file. Add these four lines IN THIS ORDER: sayHi(); then greet(); then function sayHi() { console.log("Hi"); } then var greet = function () { console.log("Hello"); };
  • Predict which call works and which throws.
  • Run the file. Note the exact error type for the failing call.
  • In a comment, explain the difference between function declarations and function expressions in terms of hoisting.
Bonus Trace the Call Stack
  • Define three functions in a JS file: multiply(a, b) returns a * b. square(n) returns multiply(n, n). printSquare(n) does console.log(square(n)).
  • Call printSquare(5).
  • In a comment, draw the call stack at the EXACT moment multiply(5, 5) is at the top — show all four frames stacked.
  • Predict the final console output.
  • Add console.trace() inside multiply and run again. Compare DevTools' stack trace with your hand-drawn stack.

Execution Context — Two Kinds

Type When How many

Two Phases

Phase Job
Creation Allocate memory for declarations
Execution Run code line by line

Hoisting — Quick Lookup

Declaration Before its line
var x undefined
let x / const x ReferenceError (TDZ)
function foo() {} Fully callable
var foo = function () {} TypeError (undefined())
const foo = () => {} ReferenceError (TDZ)

Call Stack — LIFO

Action Effect
Function called Push EC
Function returns Pop EC

Mental Model Cheats

Symptom Likely cause
undefined from a variable read var accessed before assignment
Cannot access 'x' before initialization TDZ — let/const accessed before declaration
x is not a function Function expression called before its line
Long error stack Read top-down: most recent call first
